Lesson 3 — Luồng Data End-to-End

Mục tiêu: Hiểu toàn bộ hành trình của media bytes từ khi đi vào drmpack cho đến khi ra ngoài dưới dạng encrypted segments — sẵn sàng để phát trên player.

🍕 Ví von nhà bếp: Hãy tưởng tượng drmpack là một nhà bếp pizza tự động:
  • Bạn đưa bột pizza (media bytes) vào băng chuyền
  • Nhà bếp gọi điện lấy công thức mật (DRM keys) từ nhà cung cấp
  • Lò nướng (GPAC) cắt nhỏ thành miếng và niêm phong mỗi miếng bằng ổ khóa riêng
  • Nhân viên giao hàng (Harvester) đợi pizza ra lò, kiểm tra chất lượng, rồi đặt lên xe giao hàng (output channel)

Tổng quan: 6 bước

Media bytes (fMP4) │ ▼ ┌─────────────────────────────┐ │ ① PackagingSession::push() │ ← Nhận media bytes └──────────────┬──────────────┘ │ ▼ fan-out (CENC / CBCS) ┌─────────────────────────────┐ │ ② KeyProvider::fetch_keys()│ ← Lấy encryption keys từ DRM vendor └──────────────┬──────────────┘ │ ▼ keys → XML config ┌─────────────────────────────┐ │ ③ GPAC cecrypt + dasher │ ← Mã hóa + cắt segment + tạo manifest └──────────────┬──────────────┘ │ ▼ .m4s + .m3u8 + .mpd → disk ┌─────────────────────────────┐ │ ④ Harvester::harvest() │ ← Đọc segments từ disk khi HLS manifest xác nhận └──────────────┬──────────────┘ │ ▼ Bytes → mpsc channel ┌─────────────────────────────┐ │ ⑤ PackagedArtifact → rx │ ← Consumer nhận qua async channel └─────────────────────────────┘

Chi tiết từng bước

1

Input — Nhận media bytes

src/session/mod.rs → push() → push_data()

Consumer (media-server) gọi session.push(bytes) truyền vào raw fragmented MP4 (fMP4) — đã được encode bằng ffmpeg hoặc encoder khác. Bytes chứa các ISO-BMFF box: ftyp, moov, moof, mdat.

push() làm 3 việc:

  1. Scan bytes tìm b"moof" → đánh dấu "đã có media thật"
  2. Gọi harvester.ping() → đánh thức Harvester ngay (không đợi 200ms tick)
  3. Gọi cluster.write_data(bytes) → fan-out tới mọi Representation
Fan-out là gì? Nếu bạn dùng EncryptionScheme::Dual, cùng 1 luồng media sẽ được gửi đồng thời tới 2 GPAC process: một mã hóa bằng CENC (AES-CTR), một bằng CBCS (AES-CBC pattern). Mỗi process là một Representation.

⬇

2

Key Acquisition — Lấy khóa mã hóa

src/key/policy.rs → KeyPolicyEngine::plan() → fetch_keys() → resolve()

Bước này xảy ra trước khi push(), trong PackagingSession::create(). Gồm 3 pha:

PhaLàm gìOutput
Plan KeyPolicyEngine::plan() nhìn vào danh sách Rendition + KeyMappingPolicy để quyết định cần bao nhiêu key KeyPlan — chứa KeyRequest
Fetch Gọi provider.fetch_keys(request). Provider có thể là:
  • RawKeyProvider — key cứng, dùng cho test
  • CpixProvider — gửi CPIX XML qua HTTP POST
  • SpekeV2Provider — gửi SPEKE v2 qua HTTPS
  • AxinomProvider — adapter cho Axinom Key Service
 KeySet — chứa ContentKey(s) + PsshData
Resolve KeyPolicyEngine::resolve() map mỗi key về đúng Rendition theo policy Mỗi Rendition có key + KID riêng
ContentKey là gì? Một AES-128 key (16 bytes) + một KeyID (UUID). KeyID xuất hiện trong PSSH box và manifest DRM signaling để player biết cần xin license cho key nào.

⬇

3

Encryption — GPAC mã hóa + đóng gói

src/gpac/xml.rs → generate() | src/gpac/process.rs → spawn()

Đây là bước nặng nhất — nhưng drmpack không tự mã hóa! Nó giao cho GPAC (binary bên ngoài) chạy như subprocess.

Trước khi GPAC chạy, drmpack tạo 1 file XML chứa thông tin mã hóa:

<DRMInfo type="pssh" value="...">
  <BS ID128="edef8ba9-..." />  <!-- Widevine System ID -->
</DRMInfo>
<CrypTrack trackID="1"
  crypt_byte_block="1" skip_byte_block="9">  <!-- CBCS 1:9 pattern -->
  <key KID="01020304-..." value="QUJDRA...==" />
</CrypTrack>

GPAC filter chain (3 filter nối tiếp):

stdin:ext=mp4    →    cecrypt:cfile=drm.xml    →    dasher:live.mpd
  (đọc fMP4)           (mã hóa AES)                 (cắt segment + manifest)

Giải thích:

  1. stdin filter — đọc fMP4 từ pipe (drmpack ghi vào qua BufWriter<ChildStdin>)
  2. cecrypt filter — mã hóa mỗi media sample bằng AES-128 theo mode CENC hoặc CBCS
  3. dasher filter — cắt thành segment .m4s (mỗi 2s), tạo init.mp4, viết manifest .m3u8 (HLS) và .mpd (DASH)

Output ghi ra staging directory (thường là /tmp hoặc ramdisk).

⬇

4

Harvesting — Thu hoạch segment từ disk

src/session/harvester.rs → harvest_target()

Harvester chạy background, tick mỗi 200ms. Mỗi tick nó:

  1. Quét staging directory tìm file .m3u8, .mpd, .m4s, init.mp4
  2. Đọc HLS manifest, parse segment filenames vào HashSet
  3. Với mỗi .m4s file: kiểm tra tên có trong HLS manifest không? (Manifest-Driven Readiness)
  4. Nếu có → đọc file, kiểm tra ISO-BMFF box (moof + mdat) đầy đủ → emit
  5. Xoá file khỏi disk ngay sau khi đọc vào memory (Ephemeral Staging)
Tại sao cần Manifest-Driven Readiness? GPAC ghi segment ra disk trong khi đang ghi. Nếu Harvester đọc file trước khi GPAC ghi xong → nhận được segment bị cắt nửa chừng → player crash. Giải pháp: chỉ đọc khi HLS manifest xác nhận segment đã hoàn chỉnh.
Init segment là ngoại lệ. Init segment (video_720p_init.mp4) nhỏ (~1KB), GPAC ghi atomic. Nó bypass manifest readiness và chỉ cần qua ISOBMFF completeness check (ftyp + moov box).

⬇

5

Output — Giao segment cho consumer

src/types.rs → PackagedArtifact | src/session/mod.rs → take_output_receiver()

Harvester wrap bytes vào PackagedArtifact:

PackagedArtifact {
    filename: "video_720p_1.m4s",
    data: Bytes(...),           // zero-copy, refcounted
    kind: ArtifactKind::MediaSegment,
    scheme: EncryptionScheme::Cbcs,
}

Rồi gửi qua mpsc::channel(1024). Consumer nhận bằng:

let mut rx = session.take_output_receiver().unwrap();
while let Some(artifact) = rx.recv().await {
    // Upload artifact.data lên S3, CDN, hoặc serve qua HTTP
}

Khi session.close() được gọi → stdin EOF → GPAC flush → Harvester chạy final pass → channel đóng → rx.recv() trả None.

🧠 Kiểm tra hiểu biết

Q1: Tại sao Harvester không đọc segment ngay khi thấy file .m4s trên disk?

✅ Đúng! GPAC ghi segment ra disk incrementally. Đọc trước khi ghi xong = nhận segment cắt nửa chừng. HLS manifest chỉ list segment SAU KHI GPAC ghi xong → đó là tín hiệu an toàn.
❌ Sai. Keys đã được fetch trước khi GPAC chạy, và file đã được mã hóa rồi. Vấn đề là file có thể đang được ghi dở bởi GPAC.

Q2: drmpack tự mã hóa media bằng AES không?

✅ Đúng! drmpack chỉ orchestrate: lấy key, tạo XML config, spawn GPAC, rồi thu hoạch output. GPAC cecrypt filter làm việc mã hóa thật sự.
❌ Sai. ring chỉ là dev-dependency dùng cho test. drmpack không tự mã hóa — nó giao cho GPAC binary bên ngoài.

Q3: Khi dùng EncryptionScheme::Dual, chuyện gì xảy ra?

✅ Đúng! RepresentationCluster fan-out media tới 2 GPAC process đồng thời: một CENC (AES-CTR), một CBCS (AES-CBC 1:9 pattern). Output riêng biệt.
❌ Sai. Dual mode spawn 2 GPAC process song song, không phải tuần tự trong 1 process.
