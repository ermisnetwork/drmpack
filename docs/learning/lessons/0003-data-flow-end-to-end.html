Lesson 3 — End-to-End Data Flow

Objective: Understand the complete lifecycle of media bytes from ingestion into drmpack until emission as encrypted segments — ready for playback on player clients.

🍕 The Pizza Kitchen Analogy: Think of drmpack as an automated pizza kitchen:
  • You feed pizza dough (media bytes) onto the conveyor belt
  • The kitchen calls to fetch the secret recipe (DRM keys) from the vendor
  • The oven (GPAC) slices it into pieces and seals each slice with its own lock
  • The delivery courier (Harvester) waits for pizza to emerge, checks quality, and loads it onto the delivery truck (output channel)

Overview: 5 Steps

Media bytes (fMP4) │ ▼ ┌─────────────────────────────┐ │ ① PackagingSession::push() │ ← Ingest media bytes └──────────────┬──────────────┘ │ ▼ fan-out (CENC / CBCS) ┌─────────────────────────────┐ │ ② KeyProvider::fetch_keys()│ ← Fetch encryption keys from DRM vendor └──────────────┬──────────────┘ │ ▼ keys → XML config ┌─────────────────────────────┐ │ ③ GPAC cecrypt + dasher │ ← Encrypt + slice segments + generate manifests └──────────────┬──────────────┘ │ ▼ .m4s + .m3u8 + .mpd → disk ┌─────────────────────────────┐ │ ④ Harvester::harvest() │ ← Read segments from disk when verified by HLS manifest └──────────────┬──────────────┘ │ ▼ Bytes → mpsc channel ┌─────────────────────────────┐ │ ⑤ PackagedArtifact → rx │ ← Consumer receives via async channel └─────────────────────────────┘

Step-by-Step Breakdown

1

Input — Media Bytes Ingestion

src/session/mod.rs → push() → push_data()

The consumer (such as a media server) calls session.push(bytes), passing in raw fragmented MP4 (fMP4) data — previously encoded using FFmpeg or another video encoder. The bytes contain ISO-BMFF boxes: ftyp, moov, moof, mdat.

push() performs three key actions:

  1. Scans bytes for b"moof" → marks that actual media data has arrived
  2. Calls harvester.ping() → wakes the Harvester immediately (without waiting for the 200ms tick)
  3. Calls cluster.write_data(bytes) → fans out the stream across every active Representation
What is Fan-out? If you configure EncryptionScheme::Dual, the exact same media stream is pushed simultaneously into two separate GPAC processes: one encrypting with CENC (AES-CTR), and the other with CBCS (AES-CBC 1:9 pattern). Each process represents a distinct Representation.

⬇

2

Key Acquisition — Fetching Encryption Keys

src/key/policy.rs → KeyPolicyEngine::plan() → fetch_keys() → resolve()

This step occurs before push(), inside PackagingSession::create(). It consists of three phases:

PhaseActionOutput
Plan KeyPolicyEngine::plan() inspects the Renditions list + KeyMappingPolicy to determine how many keys are required KeyPlan — containing KeyRequest
Fetch Calls provider.fetch_keys(request). The provider can be:
  • RawKeyProvider — static hardcoded keys, ideal for tests
  • CpixProvider — CPIX XML via HTTP POST
  • SpekeV2Provider — SPEKE v2 via authenticated HTTPS
  • AxinomProvider — adapter for Axinom Key Service
 KeySet — containing ContentKey(s) + PsshData
Resolve KeyPolicyEngine::resolve() maps each key to its corresponding Rendition according to policy Each Rendition receives its dedicated key + KID
What is a ContentKey? An AES-128 key (16 bytes) paired with a KeyID (UUID). The KeyID is included in PSSH boxes and manifest DRM signaling so video players know which license key to request from the license server.

⬇

3

Encryption — GPAC Encryption & Packaging

src/gpac/xml.rs → generate() | src/gpac/process.rs → spawn()

This is the heaviest step — but drmpack does not encrypt media bytes itself! It delegates execution to an external GPAC binary running as an orchestrated subprocess.

Before GPAC spawns, drmpack generates an XML configuration file describing DRM and crypt tracks:

<DRMInfo type="pssh" value="...">
  <BS ID128="edef8ba9-..." />  <!-- Widevine System ID -->
</DRMInfo>
<CrypTrack trackID="1"
  crypt_byte_block="1" skip_byte_block="9">  <!-- CBCS 1:9 pattern -->
  <key KID="01020304-..." value="QUJDRA...==" />
</CrypTrack>

GPAC filter chain (3 chained filters):

stdin:ext=mp4    →    cecrypt:cfile=drm.xml    →    dasher:live.mpd
  (read fMP4)          (AES encryption)             (segmentation & manifests)

Filter breakdown:

  1. stdin filter — reads fMP4 from the stdin pipe (drmpack writes via BufWriter<ChildStdin>)
  2. cecrypt filter — encrypts each media sample using AES-128 in CENC or CBCS mode
  3. dasher filter — segments stream into .m4s chunks (e.g. 2s), generates init.mp4, and updates manifests: .m3u8 (HLS) and .mpd (DASH)

Artifacts are written into the designated staging directory (typically a temporary path or ramdisk).

⬇

4

Harvesting — Collecting Segments from Disk

src/session/harvester.rs → harvest_target()

The Harvester runs as an async background task, ticking every 200ms. On each tick it:

  1. Scans the staging directory for .m3u8, .mpd, .m4s, and init.mp4 files
  2. Reads the HLS manifest and parses ready segment filenames into a HashSet
  3. For each .m4s file: checks if the filename is listed in the HLS manifest (Manifest-Driven Readiness)
  4. If verified → reads the file, verifies ISO-BMFF box integrity (moof + mdat) → emits the artifact
  5. Deletes the file from disk immediately after buffering into memory (Ephemeral Staging)
Why Manifest-Driven Readiness? GPAC writes segment files incrementally to disk. If the Harvester reads a file while GPAC is still writing to it, the segment would be incomplete and corrupted, causing downstream video players to crash. Manifest-Driven Readiness ensures segments are only harvested once listed in the HLS playlist, confirming completion.
Init segment is an exception. The init segment (video_720p_init.mp4) is small (~1KB) and written atomically by GPAC. It bypasses manifest readiness checks and only requires ISO-BMFF completeness verification (ftyp + moov boxes).

⬇

5

Output — Segment Delivery to Consumer

src/types.rs → PackagedArtifact | src/session/mod.rs → take_output_receiver()

The Harvester wraps buffer bytes into a PackagedArtifact struct:

PackagedArtifact {
    filename: "video_720p_1.m4s",
    data: Bytes(...),           // zero-copy, refcounted
    kind: ArtifactKind::MediaSegment,
    scheme: EncryptionScheme::Cbcs,
}

Then delivers it across an async bounded channel mpsc::channel(1024). The consumer receives items via:

let mut rx = session.take_output_receiver().unwrap();
while let Some(artifact) = rx.recv().await {
    // Upload artifact.data to S3, CDN, or serve via HTTP
}

When session.close() is called → stdin EOF is signaled → GPAC flushes remaining frames → Harvester performs its final harvest pass → the output channel is dropped → rx.recv() yields None.

🧠 Knowledge Check

Q1: Why doesn't the Harvester read a segment the moment an .m4s file appears on disk?

✅ Correct! GPAC writes segments to disk incrementally. Reading before completion results in truncated, corrupted segments. The HLS manifest only lists segments AFTER GPAC finishes writing them → making it the reliable signal.
❌ Incorrect. Keys are fetched before GPAC spawns, and encryption happens on the fly. The issue is that the file is still being written to disk by GPAC.

Q2: Does drmpack perform AES encryption internally?

✅ Correct! drmpack acts as an orchestrator: fetching keys, generating XML configs, spawning GPAC, and harvesting outputs. GPAC's cecrypt filter performs the actual encryption.
❌ Incorrect. ring is only a dev-dependency used in test mocks. drmpack delegates all media encryption to the external GPAC binary.

Q3: When using EncryptionScheme::Dual, what occurs?

✅ Correct! RepresentationCluster fans out the media stream to two GPAC processes in parallel: one for CENC (AES-CTR) and one for CBCS (AES-CBC 1:9 pattern), emitting separate outputs.
❌ Incorrect. Dual mode spawns two independent GPAC processes concurrently, not sequentially in one process.
