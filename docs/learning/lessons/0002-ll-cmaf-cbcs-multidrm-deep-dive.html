1. Data-Plane Architecture and Data-Flow Overview

drmpack is a Rust library that runs in-process inside media-server. It receives muxed fMP4 media segments as bytes, encrypts them for hardware-backed DRM systems (Widevine L1 and Apple FairPlay), packages them into Low-Latency CMAF fragments, and writes them directly to the shared-memory Ramdisk (/dev/shm) without physical disk I/O.

Pipe Demuxer (pin:ext=mp4:mstore_samples=0:mstore_purge=0) | | | | - Reads the continuous stream from the stdin descriptor | | | | - [mstore_samples=0:mstore_purge=0]: PURGE SAMPLE TABLES IMMEDIATELY (eliminates the 50-frame delay) | | | +--------------------------------------------------|--------------------------------------------------+ | | v | | +-----------------------------------------------------------------------------------------------------+ | | | 2. Common Encryption Engine (cecrypt:cfile=/dev/shm/.../drm.xml) | | | | - Reads XML configuration: scheme_type ("cenc" vs "cbcs") | | | | - CENC: AES-128 CTR mode (no crypt/skip pattern; video may still use subsample encryption) | | | | - CBCS: AES-128 CBC mode with a 1:9 pattern (10% encrypted, 90% clear video blocks) | | | | - Injects configured DRM-specific signaling/PSSH; FairPlay HLS uses separate FPS signaling | | | +--------------------------------------------------|--------------------------------------------------+ | | v | | +-----------------------------------------------------------------------------------------------------+ | | | 3. 2. Subprocess, stdin Pipe, and GPAC Input Flow (src/gpac/process.rs)

Read this section as a data flow, rather than line-by-line Rust. process.rs spawns a GPAC subprocess, connects media-server to GPAC through an stdin pipe, and configures a filter graph through which media flows as mp4dmx → cecrypt → dasher.

MEDIA-SERVER (Rust process) │ │ Segment / fMP4 bytes are already in RAM │ PackagingSession::push_segment() │ ▼ ┌──────────────────────────────────────────────┐ │ OS KERNEL PIPE │ │ │ │ Rust side GPAC side │ │ AsyncWriteExt::write_all() ───► stdin fd 0 │ │ │ │ This is an IPC buffer in kernel memory. │ │ No temporary media file is needed. │ └──────────────────────┬───────────────────────┘ │ ▼ stdin:ext=mp4 │ ▼ ┌─────────┐ │ mp4dmx │ Parses fragmented MP4 └────┬────┘ │ media samples ▼ ┌─────────┐ drm.xml │ cecrypt │ ◄── KID / KEY / scheme / pattern └────┬────┘ │ encrypted samples ▼ ┌─────────┐ │ dasher │ └────┬────┘ │ ┌───────┴────────┐ ▼ ▼ LL-DASH LL-HLS live.mpd live.m3u8 └───────┬────────┘ ▼ CMAF .m4s

2.1 Why use an stdin pipe?

If media-server already has media bytes in RAM, writing them to video.mp4 before GPAC reads them introduces an unnecessary file-I/O round trip. With Stdio::piped(), Rust writes directly to the child process's stdin. This is IPC (Inter-Process Communication) through a kernel pipe.

WITHOUT A PIPE media-server ──write──► temporary.mp4 ──read──► GPAC physical/tmpfs file THE drmpack APPROACH media-server ──write──► [ kernel pipe ] ──read──► GPAC RAM There is no intermediate media file.
Input arguments 
// GPAC reads fragmented MP4 from stdin
args.push("-i".into());
args.push("stdin:ext=mp4:mstore_samples=0:mstore_purge=0".into());
  • stdin: is the input source at file descriptor 0 of the GPAC subprocess.
  • ext=mp4: has no filename extension, so it tells GPAC that the input is MP4/fMP4 and it should select the MP4 demuxer.
  • mstore_samples=0 and mstore_purge=0: instruct the MP4 demuxer to purge memory-store data as soon as possible, instead of using the default thresholds.

2.2 What do mstore_samples / mstore_purge solve?

This is the easiest part to misunderstand. The entire pipeline should not be called “unbuffered”: the kernel pipe still has a buffer, the parser still requires internal state, and the MP4 demuxer must still wait for enough bytes to parse boxes and samples. These two options only control the memory-store purge thresholds of the GPAC MP4 demuxer.

DEFAULT MEMORY-STORE THRESHOLDS Rust ──► kernel pipe ──► mp4dmx │ │ mstore_samples = 50 │ mstore_purge = 50000 bytes ▼ [ retain data ] │ ▼ cecrypt │ ▼ dasher LOW-LATENCY CONFIG Rust ──► kernel pipe ──► mp4dmx │ │ mstore_samples = 0 │ mstore_purge = 0 │ "purge as soon as possible" ▼ cecrypt │ ▼ dasher
Important: =0 does not mean “zero buffering everywhere.” More precisely, it removes the default memory-store purge thresholds of mp4dmx, allowing progressive/live input to be released downstream as early as the parser permits.

2.3 Why is this important for 200 ms chunks?

At 30 fps, 200 ms corresponds to roughly six frames. LL-CMAF depends on dasher being able to produce small fragments according to cdur=0.2. If upstream retains data for too long, downstream cannot produce fragments early, even when cdur is correctly configured.

TARGET: 30 fps, cdur = 0.2 s Time 0ms 200ms 400ms 600ms 800ms 1000ms │──────────│──────────│──────────│──────────│──────────│ Frames [ ~6 ] [ ~6 ] [ ~6 ] [ ~6 ] [ ~6 ] │ │ │ │ │ ▼ ▼ ▼ ▼ ▼ CMAF Part 1 Part 2 Part 3 Part 4 Part 5 └──────── 1 s segment ────────┘ Low latency works only when samples can flow through mp4dmx → cecrypt → dasher early enough to produce these fragments.

cecrypt is GPAC's CENC encryptor. cfile points to a DRM configuration XML containing the KID, AES key, protection scheme (cenc/cbcs), and encryption parameters. Media samples from mp4dmx pass through this filter before reaching the segmenter.

2.5 dasher: turning encrypted samples into LL-DASH + LL-HLS

let mut dasher_opt = format!(
    "{}:dual:profile=live:dmode=dynamic:segdur={}:pssh=mv",
    manifest_path.display(),
    self.segment_duration
);

if self.latency_mode == LatencyMode::LowLatency {
    let asto = (self.segment_duration - self.chunk_duration).max(0.1);
    dasher_opt.push_str(&format!(
        ":cdur={}:asto={:.1}:llhls=br:cmaf=cmfc",
        self.chunk_duration, asto
    ));
}
  • dual: generates DASH and HLS in the same packaging graph.
  • segdur=1: sets the target segment duration to 1 second.
  • cdur=0.2: sets the target fMP4/CMAF fragment duration to 200 ms.
  • asto=0.8: is the DASH availability time offset; for a 1 s segment and a 0.2 s fragment, GPAC recommends approximately segdur - cdur.
  • llhls=br: advertises LL-HLS parts as byte ranges in the segment currently being produced.
  • pssh=mv: signals PSSH in the MPD and movie/init segment; this is a packaging choice, not a universal CMAF requirement.

2.6 Mental model to remember

process.rs = the bridge between Rust and GPAC.

media-server bytes → stdin pipe → mp4dmx → cecrypt → dasher → CMAF + manifests

mstore_samples=0:mstore_purge=0 is not a magic “zero-buffer mode”; it tunes mp4dmx to purge progressive input as soon as possible, preventing upstream retention from erasing the benefit of cdur=0.2 in the low-latency pipeline.

3. Code Walkthrough: Multi-DRM XML Generator and FairPlay Signaling (src/gpac/xml.rs)

This file translates the domain vocabulary in KeySet into the specific XML format required by GPAC’s cecrypt filter.

Lines 63–73 
let scheme_str = match config.scheme {
    EncryptionScheme::Cenc => "cenc",
    EncryptionScheme::Cbcs => "cbcs",
    EncryptionScheme::Dual => "cenc",
};

writeln!(xml, r#"<GPACDRM type="{}">"#, scheme_str).unwrap();

Technical rationale:

  • Previously, the code hard-coded <GPACDRM type="CENC">. When this attribute is CENC, GPAC forces AES-CTR regardless of the track-level attributes.
  • By making scheme_str dynamic, Apple FairPlay encryption (EncryptionScheme::Cbcs) makes the root tag <GPACDRM type="cbcs">, telling GPAC to use the AES-CBC cipher and automatically switch the HLS key method to #EXT-X-KEY:METHOD=SAMPLE-AES.
Lines 187–220 
fn build_hls_info(pssh_list: &[PsshData], key: &ContentKey) -> Result<Option<String>> {
    if pssh_list.is_empty() {
        return Ok(None);
    }

    let mut parts = Vec::new();
    for pssh in pssh_list {
        if pssh.drm_system == DrmSystem::FairPlay {
            let skd_uri = if !pssh.data.is_empty() && pssh.data.starts_with(b"skd://") {
                String::from_utf8_lossy(&pssh.data).to_string()
            } else {
                format!("skd://{}", key.kid.0.hyphenated())
            };
            parts.push(format!(
                r#"URI="{}",KEYFORMAT="com.apple.streamingkeydelivery",KEYFORMATVERSIONS="1""#,
                skd_uri
            ));
        } else {
            let pssh_box = build_pssh_box(pssh)?;
            let uri = BASE64_STANDARD.encode(pssh_box);
            parts.push(format!(
                r#"URI="data:text/plain;base64,{}",KEYFORMAT="urn:uuid:{}",KEYFORMATVERSIONS="1""#,
                uri,
                format_uuid(&pssh.system_id)
            ));
        }
    }

    Ok(Some(parts.join(",")))
}

Technical rationale:

  • Apple FairPlay requirement: Safari browsers and iOS devices refuse decryption when an #EXT-X-KEY tag uses base64 PSSH format. FairPlay requires KEYFORMAT="com.apple.streamingkeydelivery" and an skd://<KID> URI so AVPlayer can invoke its delegate to obtain the Server Playback Context (SPC).
  • GPAC’s ,URI= delimiter syntax: To make GPAC emit multiple #EXT-X-KEY lines (for both FairPlay and Widevine/PlayReady) in one rendition, definitions must live in the same hlsInfo attribute and be separated by the ,URI= delimiter. Because each item in the parts array begins with URI="...", joining them with commas using parts.join(",") produces exactly this string: hlsInfo='URI="skd://...",KEYFORMAT="com.apple...",URI="data:text...",KEYFORMAT="urn:uuid..."'.

Lines 264–272 
pub async fn push_segment(&mut self, segment: Segment) -> Result<()> {
    if self.closed {
        return Err(DrmpackError::Session("PackagingSession is closed".into()));
    }
    self.ping_heartbeat();

    let mut gpac = self.gpac.lock().await;
    gpac.write_data(&segment.data).await
}

Technical rationale:

  • Segment bytes from media-server are written directly to the GPAC child process’s stdin pipe through tokio::io::AsyncWriteExt::write_all and flush(). The data lives only in Linux kernel pipe-buffer pages and never reaches a physical disk.

5. ISO-BMFF Box Hierarchy and Hardware Decryption

Device CDM hardware (Apple Secure Enclave and Android TEE) parses an MP4 stream by traversing its binary box/atom hierarchy. Any structural discrepancy can cause decryption to be rejected (a black screen or DRM decode error).

FILE 1: stdin_dashinit.mp4 (Initialization Segment — initializes the decoder) └── ftyp (File Type: "iso6", "cmfc") └── moov (Movie Metadata Box) ├── mvhd (Movie Header: timescale, duration = 0 for live) ├── trak (Track Definition) │ ├── tkhd (Track Header: width, height, track ID = 1) │ └── mdia (Media Box) │ ├── mdhd (Media Header) │ └── minf (Media Information) │ └── stbl (Sample Table Box) │ └── stsd (Sample Description: codec profile) │ └── encv (Encrypted Video Sample Entry — replaces 'avc1') │ └── sinf (Protection Scheme Information Box) │ ├── frma (Original Format: data_format = "avc1") │ ├── schm (Scheme Type Box) │ │ ├── scheme_type: "cenc" (AES-CTR) or "cbcs" (AES-CBC) │ │ └── scheme_version: 0x00010000 │ └── schi (Scheme Information Box) │ └── tenc (Track Encryption Box) ⭐ [DETERMINES ENCRYPTION] │ ├── default_IsEncrypted: 0x01 │ ├── default_IV_size: 16 bytes │ ├── default_KID: [16 bytes UUID] │ └── default_crypt_byte_block / default_skip_byte_block: │ (For CBCS: 1:9 pattern -> byte value 0x19) ├── pssh (Protection System Specific Header - Widevine: SystemID 0xedef8ba9...) └── pssh (Protection System Specific Header - FairPlay: SystemID 0x94ce86fb...) FILE 2: stdin_dash1.m4s (Media Segment — actual video data) ├── styp (Segment Type: "msdh", "msix") └── moof (Movie Fragment Box — packages each media fragment) ├── mfhd (Movie Fragment Header: sequence_number) └── traf (Track Fragment Box) ├── tfhd (Track Fragment Header: track_ID, base_data_offset) ├── tfdt (Track Fragment Base Media Decode Time: playback timestamp) ├── trun (Track Fragment Run: duration and size of each video sample) ├── senc (Sample Encryption Box) ⭐ [IV AND SUBSAMPLE INFORMATION] │ └── contains an IV (Initialization Vector) for each frame │ └── Subsample encryption table: [bytes_clear, bytes_encrypted] ├── saiz (Sample Auxiliary Information Sizes Box) └── saio (Sample Auxiliary Information Offsets Box) └── mdat (Media Data Box) └── [Payload of video NALU blocks encrypted with AES 1:9 or full CTR]
Why do the tenc and schm boxes determine the success of Ticket 03?
When Safari receives a stream, its decoder reads the schm box in moov. If it sees cbcs, it then reads the tenc box to check the byte pattern (one encrypted 16-byte block followed by nine skipped 144-byte blocks). If these fields are correct, Apple’s CDM switches to hardware AES-CBC mode and uses the KID to request a license through the HLS skd:// URI.

The E2E test file is the sole verification point for the complete integration among Rust, the kernel pipe, and the real GPAC binary on the host.

Technical rationale:

  • duration=4: Produces exactly 4 seconds of video (120 frames). GPAC in dynamic live mode needs enough duration to establish the initial sliding-window buffer before publishing a manifest.
  • empty_moov+default_base_moof+frag_keyframe: These are essential parameters for producing Fragmented MP4 (fMP4). Without them, ffmpeg creates a regular MP4 (which needs to seek on disk to write moov at the end of the file), causing an immediate failure when it is piped into GPAC stdin.
